# AgDR-0009 — Time-ordered UUIDv7 primary keys, generated app-side

> In the context of every table carrying an application-generated primary key, facing the choice between integer sequences, random UUIDv4, and time-ordered UUIDv7, I decided that all new primary keys are bare UUIDv7 values generated in the server process with Node's built-in `crypto.randomUUIDv7()`, with no prefix and no schema change, to achieve index-local inserts and non-enumerable identifiers without a database round-trip, accepting that IDs are not strictly comparable within one millisecond, that creation time is readable from the ID, and that seeded fixture IDs stay human-readable.

Recorded 2026-10-28.

## Context

All fifteen primary keys in [the schema](../../drizzle/schema.ts) are `text` and are generated by application code, not by a database default. The identifiers that exist today:

- `lesson_draft_requests.id` and every `lesson_generation_attempts.request_id` come from `requestIdFactory`, which produced `draft_req_<uuid4>`.
- Identity scaffolding exported `createIdentifier(prefix)` as `<prefix>_<uuid4>`, with no call yet.
- Seeded fixtures use stable, readable IDs such as `tenant_demo_eu_synthetic`.

Two runtime constraints shape the choice. The deployment images and CI run Node 26 ([Dockerfile](../../Dockerfile), [foundation workflow](../../.github/workflows/foundation.yml)), which ships `crypto.randomUUIDv7()`. The database is PostgreSQL 17 locally and on Supabase, which has no `uuidv7()` function, so generation stays app-side either way.

The primary key has to serve B-tree append locality, cross-tenant non-enumeration, and stable references in URLs and logs.

## Options considered

| Option | Pros | Cons |
| --- | --- | --- |
| **A. UUIDv7, app-generated, bare** | Time-ordered inserts; opaque; 128-bit; native Node API; no dependency; already `text` columns | Same-millisecond values are not strictly ordered; leaks creation time to millisecond |
| B. Integer identity / `bigserial` | Smallest index; fastest joins; readable | Enumerable across tenants (IDOR surface); needs a database round-trip; merge and restore friction; awkward to mint before insert |
| C. UUIDv4 | Opaque; universally supported; client-generatable | Random inserts scatter the B-tree; no sort order at all |
| D. ULID | Lexicographically sortable; shorter in text form | No native support in Node or PostgreSQL; adds a dependency; weaker tooling than RFC 9562 |

## Decision

**Option A.**

1. `src/server/ids.ts` owns `createId()`, which returns `crypto.randomUUIDv7()` unchanged: no prefix, no separator, 36 characters.
2. Every new application-generated primary key uses `createId()`. The generation service's default `requestIdFactory` does; identity code does too as it lands under [#98](https://github.com/abodacs/edu-canvas/issues/98).
3. Columns stay `text`. UUIDv7 costs sixteen bytes in binary form and thirty-six in this representation; the schema does not change, and no migration is required.
4. Seeded fixture IDs are exempt. `tenant_demo_eu_synthetic` and its peers are referenced by tests, docs, and demo routes; stability is worth more than consistency here.
5. Client-side idempotency keys stay UUIDv4. They are not primary keys and the browser has no UUIDv7 API; uniqueness is all they need.
6. Identifiers are never authorization capabilities. Sessions and pending authentications keep 32-byte opaque tokens hashed at rest ([tokens.ts](../../src/server/identity/tokens.ts)).

## Consequences

- Inserts append near the right edge of each primary-key index, so page splits and cache churn stay close to sequential behavior.
- Do not order by `id`. Node fills the sub-millisecond bits randomly, so two IDs from the same millisecond sort arbitrarily; `created_at`, `attempt_number`, and `updated_at` remain the ordering columns. The migration indexes already follow this.
- Creation time is readable from the first 48 bits. That is acceptable for lesson and identity records; it would not be for secrets, which is why tokens are separate.
- No prefix means no type tag in the ID string. Logs and traces must carry the table or record kind instead of inferring it from the value.
- Removing the prefix removes the `draft_req_` shape, so any external consumer that matched on it breaks. There are no persisted production records and no such consumers.
- ULID or PostgreSQL 18 `uuidv7()` can replace the generator later without touching the schema, because the column type does not change.

## Handoff

[The design doc](../design/design-doc-implementation.md#define-records-before-wiring-providers) states the rule for new record types. `src/server/ids.ts` is the only place that mints identifiers; add prefixes, counters, or a UUID library there and nowhere else.
