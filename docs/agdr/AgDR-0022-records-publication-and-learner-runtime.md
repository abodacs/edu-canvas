# AgDR-0022 — Records, publication, and the learner runtime

> In the context of deleting prose comments from `src/server/persistence`, `src/server/records`, `src/server/publication`, `src/server/learner`, and `src/server/seed-data.ts` (AgDR-0019), facing the loss of recorded receipt, projection, bridge, and adapter contracts that the row shapes alone do not carry, I decided to consolidate the harvested decisions here, to keep the record layer the last software gate before SQL, and to accept that this page is prose read at review time.

Recorded 2026-11-21. Harvested from code comments deleted by the comment-free-source sweep ([AgDR-0019](AgDR-0019-comment-free-source.md)).

## Records boundary ([#112](https://github.com/abodacs/edu-canvas/issues/112), `src/server/records`, `src/server/persistence/records-*`)

- The command surface takes each input from its own schema, so a caller builds a valid input or fails to compile — but the implementation still parses at the store edge: a TypeScript type is erased at runtime, and this module is the last software gate before SQL, so the parse is the guard rather than a duplicate of the caller's check.
- Every write input names scope-qualified references; the referent sweep test derives the `*Id` fields from the input schemas and fails when one is missing from the sweep list, so a new unchecked reference cannot ship. Sequential reads keep the transaction ordered and stop at the first foreign referent.
- Receipts have one rule for every receipt-keyed write: `fresh` runs it, `replay` returns the stored identifiers, `conflict` means the same key was reused for different work. The operation key names the attempt; the remaining input names the work — hashing the key too would make a legitimate retry look new. `"current"` means "whatever the package's head is now": a writer with no stale-read expectation uses it, so the same intent produces the same input on a retry — which is what makes the receipt replay instead of conflict.
- A stated revision must match the head; a current-head append adopts it. Either way the row records an ordinal, a kind, and a parent true of the chain at the moment of the write, so a caller that owns no stale-read expectation does not have to guess them.
- Two concurrent writers for the same operation key can both pass the receipt lookup; the loser skips the insert and reads back the winner's committed receipt, whose result ids are the replay truth. The run-start insert carries a conflict clause arbitrating every unique index on the table, because the surface double-fires its start request (React strict mode in development, an impatient double-click in production) and a concurrent writer's committed run must win over this transaction's new id.
- A completed submission consumes one of three attempts; a replay never reaches that check because the receipt resolves first. The stored decision stands until none exists: the service computes its draft from the first response, so a retry appends evidence but never rewrites the stored decision or the stage; a teacher pause stores no decision on purpose (pause ⇒ NULL), so a paused stage keeps that choice standing too.
- The v1 tolerant reader: a run stored `{ targetId }` before decisions carried a rule version and evidence hash cannot be upgraded without inventing evidence, so it reads as "no decision yet" and waits for the next saved choice; any other unreadable value throws — a corrupt decision row must not silently become "the teacher is still choosing".
- One variant→section rule for the whole record layer: a version that links variants must resolve the assigned variant exactly; a v1 row without links falls back to the first section. The learner submit path reuses it instead of re-implementing it, so read and write paths cannot disagree.
- Projections are explicit allowlists, constructed field by field, never by deleting keys from a stored record, so a new private field cannot leak by default; `contentHash`, `packageHash`, `privateAnswerDigest`, and `privateAnswerRelationships` are absent from every projection, and `variantId` never crosses the learner seam.
- Evidence identity excludes storage timestamps: their precision differs between drivers and they are not part of what the teacher decides on.
- Server-only answer relationships live in `private-answers.ts`, which `src/shared` and any browser module must never import; the published projection never carries those values. The records port reads every table the boundary touches; write operations target only the ten record tables, and the column sets live in `drizzle/schema.ts` with the name-to-table binding forced total by type, so a new table cannot be added without a binding.
- The progress read model ([#8](https://github.com/abodacs/edu-canvas/issues/8)) reaches the projection only for runs the actor assigned inside the actor's tenant; other tenants' rows are filtered before mapping. Read-only: nothing writes or revises history. The dashboard surfaces are evidence-first: every string is stored server data rendered verbatim or a fixed local template; nothing recomputes, rewrites, or classifies a result, and every screen labels the view observational, never a mastery diagnosis.

## Publication ([#5](https://github.com/abodacs/edu-canvas/issues/5), `src/server/publication`)

- The record bridge maps an approved pack onto the canonical record model and writes the chain the learner runtime reads. Every command is receipt-keyed, so a retried publish returns the same identifiers. The mapping is lossy by design: section bodies come from the approved instructions, and the objective hash pins the approved artifact.
- What does not cross the bridge is pinned by test so carrying one later is a decision: a section carries no hints, feedback, or accessibility metadata; [#176](https://github.com/abodacs/edu-canvas/issues/176) moved the two carryable pieces (approved feedback, column labels) into the version-level `approvedCopy` block, so that key list is the contract a new section field has to argue with. The #176 deferrals: hints have no route yet, RTL metadata is [#9](https://github.com/abodacs/edu-canvas/issues/9), and the two screen-purpose fields stay teacher-facing.
- One review is one lesson: the package is named after the generation request, which survives every revision, so a revised pack appends to the same chain instead of starting a second package. The append resolves the head itself; asking for it in the input would change the input on a retry and turn a replay into an idempotency conflict.
- A teacher edit is recorded against the variant it changed; the record model names the section that variant became — dropping that list left a reviewed lesson indistinguishable from an untouched draft.
- The receipt records what the operation did and is written last: a crash before it replays the whole publish (each write recovers through its own unique key), and a replay can return the canonical assignment instead of reporting the learner link as absent. A concurrent replay may have written the same receipt; the unique record it points at is the real idempotency guard — anything else is a real persistence failure and must surface.
- Assign: `records.assign` answers FORBIDDEN when the learner is not an active student with an active membership; the publish check applies the same rule up front, so the typed refusal only fires when a membership changes mid-publish. It used to surface as a 503 "try again later", which hid the cause. A stale head or an outage is transient; an invalid input or an idempotency conflict is a server fault, not something the teacher fixes by choosing another learner.
- A private mutation never reveals whether another teacher's or tenant's draft exists (PT-20, PT-28). A retried publish returns what the first one wrote, including the canonical learner assignment, so a second click lands on the same lesson.
- The publish result type is derived from the one declaration the wire contract publishes, so the delivery seam, the client parse, and the type cannot drift — re-typing it in the handler dropped two fields and every successful publish failed the client parse.
- Without a reviewed source there is nothing to cite, so the publish writes no learner chain and the pack stays publish-only; the learner page opens the first bridged section, and the bridge maps variant i onto section i.

## Learner runtime ([#6](https://github.com/abodacs/edu-canvas/issues/6), [#7](https://github.com/abodacs/edu-canvas/issues/7))

- Grading happens in the learner service, before the record write, so a client never carries a score and a rejected submission writes nothing. Score = correct / (required + incorrect) × 100; a repeated source, an unknown source, or a target outside the answer set is incorrect; a required source with no correct pair lowers the score by omission, not penalty.
- The grading test carries a second expression of the published rule sharing no code with the implementation, so a slip in one shows up as a disagreement.
- The reveal is a pure read over one stored submission and the private answer relationships; it returns identities the learner already sent, never an answer they did not submit, and the connection sentence is an exact slice of the approved rationale.
- The next-activity decision is a checked-in table; the version string embeds a digest of the table, so a changed row without a changed version fails the unit test. It reads no clock, no client input, and no database. Prose rows carry no executable predicates on purpose: `decideNextActivity` is the one reader, and the unit test fires each row through it. The submit path and the replay read the one assisted-response rule from the same place, so they cannot disagree.
- The decision pass is deterministic and replayable from persisted rows only; the stored first response feeds it, so a retry can add evidence without changing the decision ([#7](https://github.com/abodacs/edu-canvas/issues/7): a retry appends evidence; the stored first response and decision stay; the replayed start returns the current run revision, so the next submit is never stale).
- The run model has one stage: guided evidence stays null until a multi-stage run exists, so the rule's guided rows are fixture-only (tracked in the sweep's follow-up issue).
- The learner delivery body has no score field and the schema is strict, so a tampered submission is rejected before any record work.

## Persistence adapters (`src/server/persistence/*`)

- Every read/write of postgres.js inside a transaction resolves the explicit `Promise<T>` type argument to strip the library's tuple-oriented `UnwrapPromiseArray` — the awaited value is a plain `T`.
- `on conflict do nothing` is preferred over catching a unique violation inside a transaction: postgres.js rethrows the first query error out of `begin` even when caught, so a caught constraint error would escape as a raw driver error instead of the application conflict. The records insert conflict clause arbitrates every unique index for the same reason.
- The records jsonb test binds the column list to the schema in both directions: a jsonb column missing from `recordJsonColumns` stores a JSON string scalar and the record parse reads "expected object, received string".
- RLS: the local docker role is a superuser, so a live bypass check cannot prove the policy; the catalog check proves FORCE is deployed and the cross-tenant adapter read proves query scoping. Immutable triggers block deletes, so test cleanup suspends them — production never deletes these rows.
- The limit store on PostgreSQL reserves every applicable counter and the teacher's lease in one transaction; a rejected reservation rolls back to zero consumption (nine warm-ups plus one winner — the rejected transaction rolled back its provider-call increment instead of spending an eleventh call). The seeded double mirrors the same atomicity rule; a suite not asserting limit behavior runs with a no-practical-ceiling override but still exercises the reservation path.
- Identity persistence grant stays insert-if-missing: a grant creates the tenant a fresh database lacks but never renames or rebrands a row that already exists; a tenant provisioned outside the synthetic fixture must not be renamed or marked synthetic by a membership grant. A fresh tenant gets its own standards rows inside the grant transaction so no tenant exists without the built-in catalogue ([#225](https://github.com/abodacs/edu-canvas/issues/225)). A materialized roster learner is a student identity carrying the real roster fields, so teacher-facing surfaces never render a raw machine id.
- Every `*-seeded.ts` module is a test double mirroring the PostgreSQL backend's scoping; runtime composition imports only the PostgreSQL adapters ([AgDR-0019](AgDR-0019-comment-free-source.md) §4; the boundary rule enforces it).

## Seeds and fixtures ([#110](https://github.com/abodacs/edu-canvas/issues/110))

- The seed pins the live catalog: the identifier is imported from the shared contract, not restated, so one catalog identity serves seed, compiler, and every reader. `as const` rejects a bad literal at compile time; the runtime check rejects a widened or cast value before it reaches PostgreSQL. A retired fixture identifier is not a second catalog — a record carrying it gets the documented fail-closed diagnostic, never an alias to `matching-v1`.
- The seed re-syncs its row values (`do update`); tenant provisioning stays insert-if-missing so a tenant-local row is never rebranded ([#225](https://github.com/abodacs/edu-canvas/issues/225)).
- Two seeded students once shared one display name, so the publish picker bound the identity without a membership and the film captured the wrong learner; every student a teacher can see in one class now has its own name.
- The fixture replay against real PostgreSQL provisions into a throwaway database and drops it: the fixture writes identities the seed-count parity suite also counts, and vitest orders the two files unpredictably. Two full sequential provisions on a cold database exceed the default test timeout. Provisioning itself is sequential, not `Promise.all`: several memberships share one tenant row, and concurrent grants race on the tenant insert's slug unique index, which `on conflict (id)` does not arbitrate — one loser failed the whole fixture and the composition cache held the rejected promise for the process lifetime (delegation pack case s0-smoke).
- The composition root is memoized per configuration identity: the deterministic provider keeps provider sessions in memory, so a fresh instance per request would forget them; the hosted adapter is stateless but memoizing keeps one client. Test-only hooks drop memoized instances and reset the module-scoped limiter between files.

## Consequences

- The receipt, bridge, and adapter behaviours remain pinned by the named suites; where this record and a test disagree, the test wins.
- New record tables, publication fields, or adapters extend this record instead of reintroducing prose beside the code.
